# Schema v1

This page describes the unchanged JSON profiles. The separate local database
uses [SQLite schema v1](sqlite.md#schema-and-versions), including explicit SQL
names for the distinct `W`/`w` fields.

The master is UTF-8 JSON Lines inside gzip. The discovery profile is a JSON
array, available plain and gzipped. Both are strict JSON: no NaN or infinity.
Numeric fields are parsed from MPC's fixed-width columns without rounding.
Angles may include a printed 360-degree endpoint (observed in the real source);
the producer preserves it rather than normalizing the source value.
Finite, elliptic heliocentric orbits (`a > 0`, `0 <= e < 1`, `n > 0`) are
supported. Finite non-elliptic records are counted as exclusions; malformed
records, invalid dates, duplicate keys and nonfinite values fail the snapshot.
An unknown discovery match is `null` in the master, never an invented date.
Malformed dates *present* in NumberedMPs fail validation instead of silently
reducing coverage.

| Field | Master | Discovery | Meaning / units |
|---|---|---|---|
| `id` | string | absent | `mpc:number:<decimal>` or `mpc:designation:<packed>` |
| `number` | integer or null | absent | Permanent MPC number, decoded including base-62 extension |
| `packed_designation` | string | absent | Exact MPCORB columns 1–7, trimmed; case-sensitive |
| `readable_designation` | string or null | absent | MPCORB display designation/name, columns 167–194 |
| `disc` | number or null | number | Discovery calendar date mapped to Julian day at civil midnight |
| `epoch` | number | number | Orbital element epoch, Julian day, TT (MPC packed date `.0 TT`) |
| `a` | number | number | Semimajor axis, astronomical units (AU) |
| `e` | number | number | Eccentricity, dimensionless |
| `i` | number | number | Ecliptic inclination, degrees, J2000.0 |
| `W` | number | number | Longitude of ascending node, degrees, J2000.0 |
| `w` | number | number | Argument of perihelion, degrees, J2000.0 |
| `M` | number | number | Mean anomaly at epoch, degrees |
| `n` | number | number | Mean daily motion, degrees/day |
| `orbit_reference` | string or null | absent | MPCORB reference, columns 108–116 |
| `orbit_computer` | string or null | absent | Orbit computer credit, columns 151–160 |

The discovery array has exactly `disc, epoch, a, e, i, W, w, M, n`. It preserves
the current consumers' numeric values and field names. It contains all eligible
rows by default. A positive `--limit N` selects the first N known-date supported
rows in MPCORB order **before** a stable ascending `disc` sort. Ties retain
MPCORB order. This is a limited subset, not a representative timeline sample.
The master always contains all supported rows in MPCORB order regardless of
the discovery limit. One master produces both all-record and limited exports.

Identity is independent of display names, source row order and orbital
updates. Permanent numbers remain stable after naming changes; provisional
and survey records retain their packed authority key. **A newly numbered
object receives a new number ID.** These two sources do not provide a complete
cross-identification/alias history, so v1 does not promise persistent identity
across numbering, designation corrections or merged aliases. Treat snapshots
as complete replacements. An MPC crosswalk would be a separate schema
extension before building cross-version object histories or deltas; do not
infer identity from similar orbital elements or names.

MPCORB's first 160 columns are required; later display fields are optional.
NumberedMPs v1 uses the currently verified six-digit-number fixed-width layout;
a future layout expansion fails validation and needs a parser/schema update.
`disc` represents the *published calendar date*, not an observed instant or an
accurate TT timestamp. It intentionally follows the existing importer:
2000-01-01 maps to 2451544.5. It is distinct from source Last-Modified,
retrieval/check/generation times, the element epoch, and the apps' simulation
dates. The tool does not perform time-scale corrections or precision orbit
propagation.

`schema_version` covers profile and manifest structure. `tool_version` is the
producer package version. The snapshot identity hashes a canonical ordered
JSON object containing schema/tool versions and both decoded source SHA-256
hashes. `snapshot_version` is `snapshot-v1-<full SHA-256>`. The export identity
adds the selection policy/limit and current exporter version;
`data_version` is `export-v1-<full SHA-256>`. A different limit changes the
export identity, while checking or refreshing identical decoded inputs does
not mint a new snapshot version. Tool changes affecting generated bytes must
bump the tool version; breaking schema changes must bump the schema version.

Manifests record both stored input-byte hashes and decoded-input hashes, source
URLs, acquisition mode, retrieval times, HTTP validators, source Last-Modified,
counts, exclusions, artifact bytes and hashes. `created_at` is the generation
time. Source-less metadata remains null; local import time is not claimed as
the original upstream download time. Offline imports may supply explicit saved
provenance and expected checksums. Gzip packaging changes alone do not change
the decoded-source identity. The first successful acquisition's provenance is
retained for an existing immutable version. Check observations are separate
JSON reports; they do not rewrite a release manifest.

Artifact bytes are deterministic for the same sources, tool, selection and
Python/zlib implementation. Gzip uses level 6, zero mtime and no stored filename.
Generation/acquisition timestamps and transport metadata can differ across
independent builds, so manifest bytes and their checksum are not asserted equal
between those builds. The manifest's artifact hashes, counts and content IDs
must match. Retain the original manifest for an immutable distributed version.
